### DEC-001 · Ordered milestones, no sprints
- **Context:** ATLAS has one human developer supported by two AI agents. Sprint ceremonies, story points and fixed deadlines add overhead with no team to coordinate.
- **Decision:** Track work as ten ordered milestones split into small, verifiable tasks (`docs/FEATURE_TRACKER.md`). No sprints, story points or artificial deadlines.
- **Consequences:** The order comes from task dependencies, not dates. PRODUCT_SPEC §10's sprint table is historical; the ten tracker milestones replace it.

### DEC-002 · The Markdown tracker is the single source of truth
- **Context:** Two agents update status, often in the same working tree. Hand-calculated percentages drift, and partial work tends to get counted as complete.
- **Decision:**
  - `docs/FEATURE_TRACKER.md` is the only task system.
  - Progress = Done tasks ÷ all tracked tasks, overall and per milestone.
  - The progress figures in `docs/PROJECT_STATUS.md` are generated by `node scripts/tracker.mjs --write`.
  - The validator enforces the rules: Done needs evidence and Done dependencies; Ready needs Done dependencies; Blocked must name its blocker; IDs are unique; no dependency cycles.
- **Consequences:**
  - One row per task keeps concurrent edits and Git merges line-local.
  - Adding tasks lowers the percentage; that's intended, since it reflects real scope.
  - Infrastructure tasks (FND-01, FND-02, FND-04) count toward overall progress. Status reports also state app-feature completion separately.

### DEC-003 · Agent ownership split
- **Context:** Spec §2 assigns architecture, persistence, logic, integration and builds to Claude Code, and UI/UX to Codex. Both agents work concurrently.
- **Decision:**
  - The ownership map lives in `.claude/rules/collaboration.md`, mirrored in `AGENTS.md`.
  - Claude Code's PreToolUse hook asks before editing Codex-owned paths or overwriting an existing shared file.
  - Shared docs are merged and append-only.
- **Consequences:** Cross-agent requests go through `docs/HANDOFFS.md` and the user. Each agent changes the status of its own tasks only.

### DEC-004 · Expo SDK 58 with development builds (Proposed)
- **Context:** On 2026-11-09, SDK 58 is the latest stable release (React Native 0.88.1, React 19.3, Reanimated 4.7.1, `expo-sqlite` ~58). ATLAS is installed privately, not distributed through a store.
- **Decision:** Target SDK 58. Install Expo packages with `npx expo install`. Use `expo-dev-client` builds, not Expo Go. Native folders are generated (Continuous Native Generation) and git-ignored.
- **Consequences:** On-device testing needs a development build, either local (JDK 17 and Android SDK) or EAS (Expo account). To be confirmed when FND-06 runs.

### DEC-005 · NativeWind 4.2 with Tailwind CSS 3.4 (Proposed)
- **Context:** The spec requires NativeWind. NativeWind 5 is still a release candidate, and NativeWind 4 doesn't support Tailwind 4.
- **Decision:** Use NativeWind 4.2.x with Tailwind CSS 3.4. The Tailwind config imports Codex's `src/theme` token values and never duplicates them.
- **Consequences:** Compatibility with React Native 0.88 is unproven until FND-08. If it fails, stop and present options rather than switch silently.

### DEC-006 · Data conventions (Proposed)
- **Context:** Spec §6 requires UUID keys, foreign keys, migrations, transactions, kilograms as the stored unit, history independent of routine edits, one active workout, and analytics that ignore incomplete sets.
- **Decision:**
  - UUID v4 text keys.
  - `weight_kg` stored as REAL.
  - Timestamps as integer epoch milliseconds (UTC).
  - `session_exercises` keeps snapshots, with a nullable `exercise_id` that is set to null on delete.
  - A partial unique index on `workout_sessions(status) WHERE status = 'active'`.
  - Settings stored as Zod-validated key/value pairs.
- **Consequences:** Spec-mandated parts are fixed. Storing timestamps as epoch milliseconds is confirmed at FND-10.

### DEC-008 · Global TypeScript pinned to major 6
- **Context:** TypeScript 7 (the native port) no longer ships the `tsserver` that `typescript-language-server` needs. The SDK 58 template uses `typescript ~6.0.3`.
- **Decision:** `npm i -g typescript@6` alongside `typescript-language-server` 6.0.3.
- **Consequences:** The project's own local TypeScript takes precedence once the app is scaffolded. Revisit when the language server supports TypeScript 7.

### DEC-009 · Use the `gh` CLI; no GitHub MCP server
- **Context:** `gh` is already signed in. The GitHub MCP server would need a personal access token stored in the environment.
- **Decision:** Use `gh`. Commits, pushes, merges and repo or PR creation always ask the user first (`.claude/settings.json`).
- **Consequences:** None beyond tooling. Pushes always need the user's explicit approval (see AGENTS.md).

### DEC-010 · GitHub Projects as an optional one-way mirror (Proposed)
- **Context:** The user asked for a proposed board if GitHub Projects is available. On 2026-11-09 it isn't: the `gh` token lacks the `project` / `read:project` scopes, and no GitHub repo exists yet (FND-05).
- **Proposal:** A Projects (v2) board with the columns **Backlog → Ready → In Progress → In Review → Done**:
  - One item per task, with the title `<ID> <Task>`.
  - Custom fields: `Task ID`, `Milestone`, `Owner`, `Blocked` (yes/no) and `Blocker`.
  - **Blocked** tasks sit in **Backlog** with a `blocked` label and the blocker text, because the board has no Blocked column.
- **Synchronization:**
  - The Markdown tracker stays the source of truth; the board is a **read-only mirror**.
  - A future `node scripts/tracker.mjs --sync-github` (or a GitHub Action on pushes to `main`) creates or updates items keyed by `Task ID` using `gh project item-create/item-edit`.
  - Moving a card on the board changes nothing. To change status, edit the tracker row and commit; the next sync moves the card.
  - The sync reports any card whose board status differs from the Markdown, so drift is visible rather than silently overwritten.
- **Prerequisites (user approval each):**
  - FND-05: repo and push.
  - `gh auth refresh -s project`.
  - Creating the project.
  - Then a tracker task to build and verify the sync.
- **Consequences:** Without the sync, no board is created, so there's never a second, unsynchronized task system.

### DEC-011 · Zero-cost development
- **Context:** The user has an iPhone and an Android phone, no paid Apple membership, and won't spend money on ATLAS (Codex handoff 2026-11-09). Expo's docs say Expo Go on iPhone and `eas go` need an Apple Developer Program membership; the one free iPhone route is a local development build via Xcode, which needs a Mac. SDK 58 Expo Go availability on the App Store was not confirmed.
- **Decision:** No paid services, cloud builds or memberships are prerequisites. Android: build APKs locally (free JDK 17 and Android Studio), via development builds (DEC-004). iPhone: unresolved on Windows; REL-04 is Blocked until a free route is found. No silent switch to a web app or downgrading dependencies.
- **Consequences:** On-device verification (e.g. FND-15, WKT-10) targets Android only; iPhone validation needs a Mac or a free route the user finds.

### DEC-012 · Accessible targets and shared semantic recipes
- **Context:** Fast workout logging needs generous touch targets, readable numeric text and consistent pending/error states. The product minimum is 44 points; Android's 48-unit baseline is a compatible stricter choice.
- **Decision:** Use at least 48 logical units for action targets on both platforms, tokenized scalable type/line heights, and shared semantic button/card/input recipes. Keep busy action labels readable and stable while exposing disabled/busy state; never depend on spinner or color alone.
- **Consequences:** Components reuse one token source without adding a library. Typecheck, token contrast and component behavior checks passed; native text scaling, safe areas and assistive technology still require device review. This decision does not mark DS-02 or the screen drafts Done.

### DEC-013 · Database policies from the FND-10 architecture review
- **Migrations that rebuild a table** (SQLite can't alter CHECKs, so adding an enum value rebuilds the table): the migrator runs in one transaction where `PRAGMA foreign_keys` is ignored, so with FKs on, dropping the old table would cascade-delete or null out child rows (history!). **Policy:** the startup runner (FND-11) sets `PRAGMA foreign_keys=OFF` before `migrate()`, runs `PRAGMA foreign_key_check` (fail on rows), then turns FKs on. FND-12 must include a populated-data rebuild-migration test. Never ship a rebuild migration without it.
- **Reordering** (unique `position` indexes + `position >= 0` checks): services use a two-phase update in one transaction: shift affected rows by +1,000,000, then write final positions. Tests for swap, move-to-front, insert-in-middle (RTN-03, WKT-02).
- **Clock changes:** the finish service clamps `ended_at = max(now, started_at)` so the end-time CHECK can never block finishing a workout (WKT-04 test).
- **Muscle attribution is live:** volume-by-muscle joins `exercise_muscles` at query time; history rows themselves are snapshotted. The exercise service refuses hard-delete when history exists (archive instead) and warns on muscle edits (EXL-04 test).
- **Added in schema before first use:** `workout_sets.target_*` (plan vs actual, WKT-01), `workout_sessions.rest_timer_ends_at` (WKT-05), `exercises.builtin_key` unique (idempotent seeding, EXL-02), FK-child indexes, `(status, started_at)` index, two-way completed/`completed_at` check.
- **Open for downstream tasks:** muscle/equipment vocabularies as Zod enums (EXL-01); RPE step size (Zod); bodyweight volume semantics (ANL-01/02); reject tracking-type change when routine targets exist (EXL-04); `.sql` loading for Metro/Jest (FND-11/12).

### DEC-014 · Domain contract conventions (FND-13 review)
- **RPE:** 1 to 10 in half-point steps in Zod (the database CHECK only enforces 1 to 10, so Zod is stricter; imports and restores must validate with Zod). Closes the RPE item left open in DEC-013.
- **Rest durations:** one range, 0 to 1800 s, for per-exercise rest and the default rest setting (0 = no rest; the settings schema uses the same schema, with round-trip tests at 0 and 1800). Only a running rest timer needs 1 to 1800 s.
- **Errors:** `message` and `details` are safe to show. The low-level error is kept only in `Error.cause`. Services translate repository failures into `PERSISTENCE`; unexpected bugs surface as `INTERNAL` (not retryable). `SESSION_ACTIVE` is used when a delete targets the active session.
- **Update schemas never carry defaults:** a partial update contains exactly the keys sent (Zod 4 would otherwise refill defaults and wipe fields).
- **Ids:** Zod 4 `z.uuid()` rejects non-RFC ids (including the nil UUID); seed rows use real v4 ids and identify built-ins by `builtinKey`.
- **Read schemas vs stored rows:** domain schemas trim and limit text (names 1-100). Restore/import code must validate and normalize rows, not assume stored text already fits.

### DEC-015 · Own migration runner and tracking table
- **Context:** drizzle's `migrate()` runs all migrations in one transaction with foreign keys on, where a table-rebuild migration wipes history (reproduced in `tests/integration/migrations.rebuild.test.ts`; DEC-013).
- **Decision:** `src/database/migrate.ts` applies drizzle-kit's generated SQL itself (foreign keys off, one transaction, `foreign_key_check`, commit, foreign keys on) and tracks applied migrations by journal **tag** in `__atlas_migrations`. drizzle-kit remains the generator; its journal and SQL files are the input. The drizzle tracking table is not used.
- **Consequences:** migrations are keyed by tag, so tags must never be renamed or reused. A database from a newer app is refused. drizzle's built-in migrator must not be used on this database. The runner is single-flight (one shared expo-sqlite connection), reads back every safety pragma, uses `BEGIN IMMEDIATE`, and its whole-database `foreign_key_check` means imports must never create orphan rows.

### DEC-016 · Local Android build workarounds (Windows, this network)
- **Context:** the first local debug build needed 13 attempts. Causes, in order: (1) Cloudflare in front of `repo.maven.apache.org` answers Gradle with HTTP 403 on this network; `plugins.gradle.org` redirects library requests there too. (2) Declaring a plugin repository disables Gradle's default plugin portal. (3) Intermittent AccessDenied renaming build-cache files (retry fixed it). (4) Windows 260-character path limit: the SDK's CMake 3.22.1 ships an old ninja that is not long-path aware, and CMake embeds the full source path (react-native-reanimated's generated code) in object paths (314 characters). A drive alias (`subst`) does not help because Gradle and Node resolve it back to the real path.
- **Decision:** (a) route Maven Central through Google's official mirror (`maven-central.storage-download.googleapis.com`) with an init script, mirror first in every repository list and the plugin portal kept after it; (b) use a short Gradle home `C:\Users\Admin\gh` via `GRADLE_USER_HOME` so no global Gradle config changes; (c) relocate C++ build folders to `C:\Users\Admin\gb\<module>`; (d) use CMake 3.31.6 (ninja 1.12.1, long-path aware) via `cmake.dir` in the generated `android/local.properties`, from the Android SDK repository with its published checksum verified. All in `scripts/android/`.
- **Consequences:** builds work from the existing project location without moving it or changing Windows or antivirus settings. The init script only applies when `GRADLE_USER_HOME` is the short home. If the network block disappears, step (a) can be dropped. If Reanimated-style long paths appear in new modules, (d) already handles them. A project path under about 60 characters would remove the need for (c) and (d).

### DEC-017 · GitHub repository stays public
- **Context:** PRODUCT_SPEC §1 requires private *distribution* of the app (no public release, store or accounts). FND-05 originally also asked for a private repository. The repository `github.com/brtbrt123/Atlas` already exists and is public; Claude Code asked and the user chose to **leave it public** (2026-11-09).
- **Decision:** the repository stays public. The app itself is still privately distributed. The "private repo" acceptance criterion of FND-05 is replaced by "a GitHub remote exists; visibility is the user's decision".
- **Consequences:** everything committed is world-readable. Never commit secrets, credentials, signing keys, `.env` files, session logs or personal data (already git-ignored or denied in `.claude/settings.json`); keep device serial numbers and local user paths out of new docs where practical. Pushes still need the user's explicit approval each time (AGENTS.md). Git history is permanent: a mistaken commit means rotating the secret, not just deleting the file.

### DEC-018 · Exercise vocabularies and repository pattern (EXL-01)
- **Vocabularies:** fixed lists `MUSCLES` (19 values, anatomical groups only, no `cardio`/`full_body`, `shoulders` is final) and `EQUIPMENT` (19 values, non-overlapping, rules in CONTRACTS.md) in `src/types/enums.ts`, validated by Zod, stored as text without CHECK constraints. Only additions are allowed later (stored values are never renamed). This closes the open item from DEC-013/DEC-014 and makes `muscle`/`equipment` stable for Codex.
- **Repository pattern:** factories over the drizzle instance, synchronous because the drizzle expo-sqlite driver is synchronous; domain types in and out, no Zod, no clock, no ids. Services add validation, ids, timestamps and error translation.
- **Test strategy:** repositories run against the **real drizzle expo driver** in Jest through a small fake of three expo-sqlite methods over `node:sqlite` (`tests/helpers/drizzleDb.ts`), instead of mocking Drizzle or using a different ORM driver.
- **Consequences:** the fake could diverge from real expo-sqlite behavior; the first on-device exercise flow (EXL-09) is the final check. Large operations (catalog seed, import) must be chunked.
- **Review fixes (architecture review of EXL-01):** repositories accept an executor that may be a transaction, patch semantics are `undefined` = unchanged / `null` = clear, no `this`, the test fake mimics expo's plain error shape and real change counts, duplicate muscles are rejected by Zod.
- **Sync API rules (bulk operations):** repositories stay synchronous (services expose Promises). After startup the expo-sqlite async API must not be used on the drizzle connection, and `db.transaction` callbacks must never be async. Import/restore (SET-04) runs as ONE synchronous transaction behind a blocking "Restoring..." screen (atomic; acceptable for a single user); the catalog seed (EXL-02) is one transaction and its duration is measured on the Infinix device. `busy_timeout = 5000` stays (single connection, so lock waits are not expected); revisit if a second connection is ever added.
- **Built-in catalog policy (decided now for EXL-02):** seeding is an idempotent insert-if-missing by `builtinKey` in one transaction and never overwrites user edits or `isArchived` on existing built-ins; a catalog upgrade adds new exercises only.

### DEC-020 · Proposed visual direction: clean, light, pastel red (Claude Code, 2026-11-09)
- **Context:** the user found the exercise screens plain and asked Claude Code to redesign them in Figma. The user rejected a first dark pass with color glows ("I don't like the gradient") and asked for a clean UI in the spirit of the GoTyme and Maya apps, in pastel red. PRODUCT_SPEC §5 already warns against gradients and glowing borders.
- **Decision (proposed, awaiting the user's approval):** a light, flat UI. Light grey canvas `#F6F6F8`; white cards with a soft 6% shadow; one accent, pastel red `#FF6961`, for actions, selection and progress, with dark text `#45141A` on it (5.4:1). Red text and icons use strong red `#C2332C` (5.5:1 on white). Plus Jakarta Sans for all text. Soft pastel colors label the six muscle groups (chest, back, shoulders, arms, core, legs) and are never used for actions. A segmented front/back body map shows primary muscles at 100% and secondary muscles at 55%. No gradients or glows. Tokens are Figma variables in the collection "ATLAS / Color", with a Light (default) mode and a Dark mode that keeps the same accent.
- **Where:** the user's Figma file, section "ATLAS — Redesign" (six screens and a Foundations sheet) and section "ATLAS III — Components". Codex's ATLAS II frames and the original "ATLAS" variables are untouched. The file link is not recorded here because the repository is public.
- **Consequences if accepted:** the design-token line in PRODUCT_SPEC §5 is replaced (user decision); Codex updates `src/theme` tokens, `docs/DESIGN_SYSTEM.md` and the screens through the DS and EXL tasks; Claude Code adds the font package (and `react-native-svg` if the body map ships as SVG) under a new decision record. Until then nothing changes in code. Figures in the frames (counts, bests, dates) are illustrative.
- **Accepted** by the user on 2026-11-09 (implementation dependencies: DEC-021). PRODUCT_SPEC §5 now lists the new tokens. For the record, the superseded spec tokens were: background `#101418`, surface `#1E252B`, elevated `#293239`, accent `#B7F36B`, primary text `#F5F7F8`, muted text `#A6B0B7`, border `#344047`, danger `#EF7777`. The user's generated pictures and the traced muscle model are in `assets/images/` (HANDOFFS 2026-11-09).

### DEC-021 · Font embedding and SVG support for the approved look (Claude Code, 2026-11-09)
- **Context:** DEC-020 needs the Plus Jakarta Sans font and an SVG body map. ATLAS runs as a development build (not Expo Go), so native changes are possible, and everything must work offline.
- **Decision:** add `expo-font` (~58.0.11), `@expo-google-fonts/plus-jakarta-sans` (^0.4.2, OFL font) and `react-native-svg` (15.16.0) with `npx expo install`. Embed the five weights (400–800) at build time with the `expo-font` config plugin instead of loading them at runtime: Android gets one XML font family named "Plus Jakarta Sans"; iOS lists the files in `UIAppFonts` and takes the family name from the files. Screens use `fontFamily: 'Plus Jakarta Sans'` with `fontWeight`; the root layout has no font-loading state. The native background, splash and `userInterfaceStyle` switch to light.
- **Consequences:** the font and `react-native-svg` work only after a new development build (prebuild and Gradle, DEC-016); the current dev client shows system fonts and cannot render Svg, so Svg screens must not be tested on it. iOS stays unverified until an iPhone build exists (DEC-011). Jest is unaffected. The status bar style in `app/_layout.tsx` stays light until Codex's light tokens land, then flips to dark in the same change. The font license ships inside the package; keep it with the files if they are ever copied.
